담기·가져오기 로딩 — 제안

“양이 많으면 바로 반영이 안 된다”는 게 정확한 관찰입니다. 원인이 로딩 표시가 없는 것만이 아니라 요청을 하나씩 순차로 보내는 구조에 있어서, 로딩 UI와 함께 그쪽도 같이 봐야 합니다.

1. 지금 무슨 일이 일어나는지

지점지금결과
링크 저장 createLink가 단건 insert(links.ts:36)이고 saveWindowInto가 for … await로 순차 호출 탭 30개 = 왕복 30번. 한 번에 ~120ms만 잡아도 3.6초
완료 후 재조회 loadCollections()는 collectionsLoaded를 건드리지 않는다 (재조회 핸들러는 스켈레톤을 띄우지 않도록 의도된 설계) 그 사이 화면에 아무 표시가 없다 → “안 눌렸나?”
카드·버튼 진행 중에도 비활성되지 않는다 두 번 누르면 컬렉션이 두 벌 생긴다 — 로딩과 별개의 실제 버그
공유 코드 다이얼로그 「추가」가 disabled는 되지만 라벨은 그대로 눌렸는지 알 수 없다
아는 정보 담을 탭 수, 창별 개수 / 코드 조회 결과의 title·link_count 완료 전에 결과의 모양을 이미 알고 있다 → 진짜 스켈레톤이 가능

누른 즉시 결과의 골격을 그립니다. 창별 컬렉션과 링크 자리를 실제 개수만큼 미리 놓고, 도착하는 대로 채웁니다. 기다리는 화면이 아니라 만들어지는 화면이 됩니다.

4. 공유 코드 — 버튼 상태와 이후

여기는 서버 RPC 한 번이라 진행률이 없습니다. 버튼 상태로 알리고, 닫힌 뒤 보드에 골격을 놓습니다.

5. 적용 순서 제안

  1. 중복 클릭 막기 (지금 당장). 진행 중 카드·버튼 비활성. 로딩 디자인과 무관하게 컬렉션이 두 벌 생기는 버그를 먼저 막아야 합니다.
  2. 벌크 insert. createLinks(client, inputs[])를 만들어 .insert(배열) 한 번으로. 창 3개면 왕복이 36회 → 6회가 되고, 체감 지연 대부분이 사라집니다. 가장 값싸고 효과가 큰 조치입니다.
  3. 낙관적 골격(L3). 벌크로 빨라진 뒤에도 남는 0.3~1초 구간을 덮습니다. 여기까지 하면 “바로 반영 안 된다”는 느낌이 없어집니다.
  4. 실패 롤백. 낙관적 UI의 필수 조건 — 실패하면 골격을 걷고 「담지 못했어요. 다시 시도해 주세요」를 띄웁니다. 부분 성공(일부 링크만 저장)이면 저장된 것은 남기고 실패 수를 알립니다.
  5. 되돌리기(선택). 「열린 창 전부」는 한 번에 컬렉션 여러 개를 만듭니다. 완료 토스트에 되돌리기를 붙이면 낙관적 UI의 위험이 상쇄됩니다 — Toast에 액션 슬롯이 필요합니다.
